## 편집 반응 속도

같은 프로브를 수정 전 코어와 수정 후 코어에 각각 링크해 측정했다. Apple M4 / Mac16,1 / 16GB / macOS27.0(26A428), 합성 fixture, 2초 클립을 연속 배치한 단일 영상 트랙이다. 실사 소재·다중 트랙·프록시 조합의 수치가 아니다.

| 클립 수 | 타임라인 | 수정 전 build | 수정 후 build | 수정 전 컴포지션 영상 트랙 | 수정 후 |
|---:|---:|---:|---:|---:|---:|
| 30 |60초|1.317초|0.055초|31|2|
| 60 |120초|2.304초|0.054초|61|2|
| 120 |240초|4.529초|0.064초|121|2|
| 300 |600초|11.510초|0.070초|301|2|

수정 전에는 편집 1회마다 타임라인 길이에 비례해 조합을 다시 만들었다. 수정 후에는 캐시한 carrier를 반복 삽입하고 클립을 겹치지 않는 레인에 패킹하므로 사실상 상수다. 트랙 수는 클립 개수가 아니라 최대 겹침 깊이를 따른다. 표의 수치는 `TimelineRenderer.build` 소요 시간이며 출력 인코딩 시간이 아니다.

라이브 미리보기는 1개 영상 클립 프로젝트에서 측정했다. 60Hz로 1초 드래그할 때 55틱 중 **47회**를 실제로 렌더링했고, 동기적으로 몰아친 30틱은 1회로 합쳐졌다. 드래그 30틱의 실행취소 비용은 1단계다. `live-checks.json`의 단건 45ms는 프로브의 20ms 폴링 간격이 포함된 값이므로 상한으로 읽는다. 큰 실사 프로젝트의 수치는 다시 측정해야 한다.

## 출력 형식

| 항목 | 이전 | 현재 | 증거 |
|---|---|---|---|
| 캔버스 | 축당 1920 | 축당 4096 · 총 9.4메가픽셀 | 3840×2160 30프레임, 4096×2160 24프레임 실제 디코딩 |
| 프레임레이트 | 30만 | 23.976/24/25/29.97/30/50/59.94/60 | 8종 모두 24프레임 요청에 24프레임 출력 |
| 비트레이트 | 4·8·16Mbps | 4·8·16·24·40·64Mbps, 해상도 기준 자동 제안 | 1080p30=8, 2160p30=24, 2160p60=40Mbps |

29.97은 30과 다른 타임베이스를 유지한다(60프레임 = 2.0017초). carrier 캐시는 반올림 fps가 아니라 정확한 유리수로 키를 만든다. 4096 초과 캔버스와 미검증 프레임레이트(48fps)는 렌더링 전에 거부한다. **4K 입력 소재의 디코딩 성능과 HDR 변환은 여전히 미검증이다.**

이 작업 중 `MediaInspection`이 H.264의 누락된 샘플 길이를 1/30로 보정하던 것을 찾아 고쳤다. 30fps 외 모든 출력의 길이를 잘못 측정하던 검증 도구 자체의 결함이었다.

## 실제 GUI

- 0.2 문서를 0.3에서 열고 검증 사본을 저장했다.
- 15초 BGM 원본을 실제 분석: peak -3.1dBFS, RMS -18.2dBFS, 44.1kHz 2채널, 무음 후보 1개. 정규화 볼륨1.266567 적용 후 Undo로0.25 복구.
- 1초 페이드가 있는 BGM의 앞0.5초를 잘랐다. sourceStart=1/2, start=1/2, duration=29/2를 저장·재열기. 436개 키로 기존 음량 envelope 보존.
- 처음 발견한 일반 H.264 프록시 생성 실패를 수정하고, 최종 앱에서 같은 영상3개 생성·사용을 확인했다.
- 프록시 미리보기를 켠 상태로 16Mbps 옵션 MP4 출력 성공. 원본 출력 계획을 별도 생성하며 프록시 계획 직접 출력은 엔진이 거부한다.
- 실제 결과: 1080×1920, 30fps, 450프레임, 15초 H.264/AAC, monotonic PTS. 오디오 종료14.9994375초. 디코딩한 한국어 자막·PNG·엔드카드 이미지 확인.
- 출력: Artifacts/Upgrade-GUI/GUI-0.3-final-16Mbps.mp4. 검사: Artifacts/GUI-0.3-Final/output-inspection.json.
- 외장 ExFAT 수집의 파일 이동·임시 inode 차이를 수정했다. 실제 T7에서 수집·해시·동시 저장 12회·64MB 복사 중 취소·외부 파일 보존을 통과했다. 최종 앱 GUI에서도 원본8개 수집·전부 SHA-256 일치·수집본 재열기·미리보기 준비를 확인했다. 기록: Artifacts/GUI-0.3-Final/collection-checks.json.
- APFS는 지원되는 독점 디렉터리 이동으로 확정한다. ExFAT은 새 폴더 독점 예약 후 파일을 복사하므로 작업 중 폴더가 보일 수 있다. Project.jhcut을 마지막에 기록하고 완료 알림 이후 사용한다.
- Liquid Glass 재디자인 후 실제 앱을 실행해 스크린샷으로 확인했다. 통합 툴바·문서 제목·유리 재생 컨트롤·속성의 출력 형식 선택이 모두 렌더링된다. 접근성 트리에 `실행취소`·`라이브러리 접기`·`프로젝트 저장`·`미디어 검색`·`안전 영역 보기`가 노출되는 것을 확인했다.
- **아직 손으로 확인하지 않은 것:** 슬라이더 드래그의 체감, 4K 프로젝트의 실제 재생 부드러움, 패널별 세부 레이아웃. 엔진과 모델 계층은 228개 자동 검사로 확인했으나 SwiftUI 본문 자체는 스크린샷 수준까지만 봤다.

## 남은 범위

한국어 모델 설치 승인과 실제 인식, 4K 입력 소재 성능, HDR/Log 변환, 연결 클립, LUFS/리미터/EQ, 마스크/추적/속도 곡선/멀티캠/고급 전환/협업, macOS14·Intel 실기기, 장시간 실사 성능, 실제 디스크 고갈·외장장치 강제 분리, 공개 배포 공증은 미완료 또는 미검증이다.

속성 변경마다 사용 원본을 다시 검사하는 동작(E15)은 그대로다. carrier 캐시를 처음 만들 때의 1회 인코딩은 여전히 취소를 확인하지 않는다(E18). 두 항목 모두 [엔진 감사](AUDIT-ENGINE-0.3.md)에 남겨 두었다.

0.2에서 수행한 60초·600초 출력/소재154개 검증은 [당시 기록](STATUS-0.2.md)이다. 0.3에서 동일 장시간 회귀를 새로 수행한 것처럼 합산하지 않는다.
